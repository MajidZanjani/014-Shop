# Local archive worker boundary — design and current scope

Current local runtime6bae131 has exact capture/root binding, explicit bounded authority, fenced claims and bound-root publication/reopened readback with unique technical verification. See07-02-PUBLICATION-PARTIAL and07-02-PUBLICATION-RACES. No automated queue loop or provider/domain qualification exists. Remaining sections preserve the earlier design rationale; their original proposed next actions are historical, not current missing-capability claims.

## First resolve destination and durable authorization

Choose only an explicit existing owned0700 disposable local archive directory for synthetic tests. Bind an immutable destination/configuration identity to the intent before the first publication claim. Verify the actual opened directory and private metadata through its descriptor, not a caller-supplied display path. Reopen/restart must recognize the same bound destination; replacement/wrong roots fail closed, never silently rebind an uncertain operation. Namespace/receipt configuration must be versioned and testable. Do not infer remote storage, Object Lock, off-host custody or allowed production writes from a local root or profile string.

Worker access is an internal restricted service capability, not a browser session or public download. Capture attribution is historical and must not be rewritten to refresh authority. Define which durable authority/revision governs archive work and how revocation/ownership/source changes hold it. A stale staff MFA timestamp cannot be relabelled recent, and a lost browser session cannot be invented. Start with conservative local holds when authorization cannot be revalidated. Held work needs explicit reconciliation/reauthorization semantics before any resume interface is added; do not silently clear holds on ordinary capture retry. Archive bytes already published remain retained after revocation and never authorize a human read or a business effect.

## Proposed claim/publish/readback protocol

1. Extend the intent schema additively with a bounded lease, random token, increasing generation, attempt count and explicit bound destination reference. Constraints pair leased state with all lease fields and clear lease fields for other states. Keep local/prepared classification and false qualification/effect flags enforced. A technical local-verified state never means accepted, performed, paid or provider-qualified.
2. Claim one eligible exact envelope/destination in a short PostgreSQL transaction. Recheck immutable payload/hash/length, source scope and durable authority/hold state. Increment/fence generation. Commit before any filesystem/storage call. Never reuse Probe/FakeReceipt or hold a database transaction over publication.
3. Publish the same stable envelope identity and exact bytes to the already bound destination; verify receipt identity/hash/size/classification, reopen/readback and compare bytes. Uncertain acknowledgement is reconciled with this identity, not a fresh key/root or deletion. Busy/unavailable local storage remains pending/held under bounded policy; no automatic paid/provider fallback.
4. Complete in a new short transaction only when token/generation, lease validity, envelope hash/identity, destination and authorization/hold revision still match. A stale/stolen/expired/revoked worker cannot mark success. Every observation is retained with safe fixed error categories; no private values/paths/tokens in ordinary output.
5. No publication/acceptance/payment/delivery/support effect may follow from this local verification. Qualified retention, domain-specific actual completion and later financial/dispatch ordering require their own actual contracts/evidence.

## Bounded local work authorization — implemented subset and remaining proposal

Explicit issuance/revocation records and shared-source detached inspection are implemented (07-02-AUTHORITY-PARTIAL,07-02-INSPECTION-PARTIAL). Claim/lease protocol and work execution below remain proposals, not runtime capability or deployment permission. Destination binding3b9f6a1 is necessary but does not authorize detached reads/publication. Do not expand intent states first and infer authority afterward.

Introduce an explicit internal authorize_request_archive(request, intent_id, expected_destination_id, command_id) action. It must own its durable outer commit, reject external transactions and validate current local/synthetic fake settings. Reuse the exact request producer and current owner/recent-MFA staff/private-scope authorization. Compare retained envelope bytes/hash/length, original owner and actual destination binding. No filesystem call occurs under its transaction. This deliberate action grants only bounded prepared-byte work to that exact immutable envelope/root; never customer downloads, offers, acceptance or domain effects. No automatic grant from capture/binding, no stored browser session and no fabricated request for a detached worker.

Proposed additive immutable authorization record: UUID, intent, unique command_id per intent, increasing intent authorization generation, destination, envelope digest/length/schema, owner and authorizing actor, issued_at/not_after, recorded staff credential generation/MFA time when applicable. Store no bearer token/session/cookie or private payload copy. A separate revocation/hold event records actor/time/fixed reason against the grant; never overwrite historical attribution. Exact command retries may return the original record only; expiry/revocation stays expired/revoked. New commands require fresh interactive authorization and expected generation. No implicit held-work resumption: explicit reauthorization must name the held generation/reason after reconciliation. Bound the proposed local lifetime to five minutes, with no automatic renewal; this is a synthetic implementation limit, not approved commercial policy.

Detached claim rechecks the grant deadline/revocation/generation, exact retained source/destination/owner and active account. For staff-origin grants also require the same enabled credential generation and exact current quotation/private-scope assignment. Session expiry is handled by the explicit short grant deadline; historical MFA is never marked current. Owner identity must still be active/verified and match the original cart owner. Unknown/deleted scope, changed source or invalid immutable bytes holds work with fixed safe categories. Rebuild/compare from a shared locked scope reader factored from prepare_request_envelope, without constructing a browser session or bypassing its snapshot checks. The grant check cannot substitute for that source comparison.

Lock order must follow existing request producer: staff credential when applicable, quotation/cart, then retained envelope, intent and grant/revocation state. Enrollment and revocation paths must use compatible ordering and PostgreSQL serialization. Account/grant updates that currently do not share locks require explicit design/tests before making any stronger revocation guarantee. Recheck at completion. Revocation during unlocked storage I/O can leave retained prepared bytes, but must prevent successful completion/return; never promise prevention of already-started physical writes.

Only after these records/readers/revocation tests exist should a separate slice add leased state. Proposed lease: server-generated token, monotonic generation, attempt count and bounded database-clock deadline; no caller supplied deadline/token. Claims skip locked eligible rows, cannot claim held/revoked/expired work and commit before publication. Completion compares token+generation+authorization generation+destination+deadline and rechecks authority. Expiry/reclaim fences old workers. Store fixed failure categories and retained receipt metadata without exposing private bytes, paths, tokens or business values in logs. State expansion also requires updating capture/binding retry semantics so exact capture does not create replacement intents or reject legitimate retained terminal records without a defined safe outcome.

Required actual PostgreSQL tests for the authority slice: absent grant cannot claim; explicit current request required; exact retry does not extend deadline; cross-owner/destination/digest mismatch; stale expected generation; disabled identity/credential and removed/changed private grant; concurrent grant/revoke; historical staff attribution unchanged; held work never auto-clears. Lease tests follow separately. Every new status must preserve false retention/effects flags. Until then current runtime remains pending/held only.
