# Shop secret custody and deployment gates

Operator resource credentials are available in repository .env. Read only the needed value for an authorized operation without printing it. If absent/empty, add a clearly named blank entry/purpose preserving existing values, then ask the user to fill .env directly. No current synthetic build/test needs those credentials.

Runtime application secret key and the new shop database password are separate private files, mounted individually read-only as /run/secrets/shop/secret_key and database_password. No application .env loader, image/store secret, ordinary secret environment, URL or credential dump. Container user 10001 maps to the new qualified shopsvc identity; actual file ownership/mode access must be proven off-host, then qualified for mx1. Production settings enforce bounded regular private files. Secret provisioning/rotation is not performed by the build.

All deployment definitions are candidates and disabled by default. No UID/GID/subordinate range, occupied listener, existing mount/dataset, ingress or public certificate ownership is invented. The Nix module requires explicit qualified IDs, nonoverlap and actual image digests. The readonly startup guard requires root-controlled current machine/account/dataset/PG checksums/system identifier/paths/resource evidence; absent mounts or a new empty PGDATA must fail, never initialize elsewhere. Initial independent cluster bootstrap, password/hba policy and every mutating command require separate exact ownership/destination attestation. ops/runtime/database.py now provides a single-statement INSERT/UPDATE/DELETE execution primitive. It checks actual PostgreSQL system identifier/data directory/database/session and current role/endpoint/durability on the same connection and transaction before DML and before commit, requires fresh runtime evidence both times, and rolls back on denial without automatic retry. The host-side process callback now exists in ops/runtime/process_probe.py and is tied to the SQL primitive through execute_operator_mutation. Real runtime validation, operator command/credential plumbing, and Django/worker integration are still pending. Bootstrap, migrations and other command families remain unimplemented. This is trusted internal SQL, not an interface for user-supplied queries. Metadata reads need narrowly reviewed PostgreSQL privileges; no superuser grant is implied.

No existing PostgreSQL, management socket, privileged/host-network container or shared journal configuration is used. Rootless runtime prerequisites (user namespace helpers, cgroup v2 delegation, storage, generator discovery and selected network stack) need qualification. The module deliberately does not enable global Podman, alter global subordinate-ID helper wrappers or manage all users' lingering. Its new shop-specific linger action is still subject to full activation-impact review before any actual write.

The parent ZFS quota is proposed 80 GiB including descendants/snapshots; the PostgreSQL subtree quota is proposed 50 GiB including data/index/WAL. All GraphRoot/images/volumes/temp/log/certificates/spool and owned backups belong underneath. Actual all-descendant cgroup/helper containment and all writable path accounting are pending off-host tests. A declaration or passing guard does not prove them. Never run disruptive tests on mx1, existing containers or MicroVMs. See docs/qualification-runner.md; no runner assigned.

Pending separately: new component/transitive/bundled licence review, image builds/digests, generated Quadlet compatibility, rootless lifecycle/exhaustion/recovery, immutable database startup/bootstrap wrapper, unchanged public ingress/TLS, actual inventory and complete activation impact. No host activation, DNS/TLS, provider spending or production readiness is authorized by these files.

Local SQL verification: `nix develop ./ops/nixos --command python3 scripts/check.py database-destination`. It creates two token-owned disposable PostgreSQL clusters with synthetic data only. Container/account evidence is a fixture, and the canonical production PGDATA comparison is explicitly adapted in the test to the exact owned scratch path. This lane cannot establish real rootless container or mount identity, and does not satisfy deployment-boot. Implementation follows the official [Psycopg transaction contract](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [prepared-statement constraint](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html) and [PostgreSQL server-identity functions](https://www.postgresql.org/docs/18/functions-info.html).

The host-side process probe loads `/srv/shop/control/database-process.json` only through root-owned, non-group/world-writable, non-symlink ancestors and a bounded regular root-owned file. Its closed record binds the existing startup evidence and SQL destination to an exact PID/start tick/executable/cgroup. Every call rechecks the startup guard, then reads the pinned process directory: PID start time before/after; exact host UID/GID; zero capabilities/no-new-privileges; rootless UID/GID maps with container10001 mapping to the approved host account; exact qualified cgroup including container scope; exact PostgreSQL executable; and the same device/inode/owner for host PGDATA and the process-root PGDATA mount. No Podman command, init, mount, namespace entry, target discovery, record refresh or repair occurs. A restart makes the recorded PID/start time stale until separately authorized evidence refresh; this module cannot approve its own new target.

`execute_operator_mutation` obtains SQL identity from that same record and refuses record changes between checks. It is a **host-side library primitive**, not a deployed operator CLI or an application permission to mount host /proc/control/management resources. Application and worker integration needs a compatible design that retains existing container isolation. Actual runtime permissions (including proc visibility, namespace mapping and pg_controldata/ZFS reads), exact supported scope names and real post-restart behavior remain off-host qualifications. Synthetic parser/loader/wrapper tests do not establish those capabilities. No control record or sample populated PID/UID is installed by this change.

Process-field references: Linux [process start time](https://www.man7.org/linux/man-pages/man5/proc_pid_stat.5.html) and [user namespace mappings](https://man7.org/linux/man-pages/man7/user_namespaces.7.html). The expected cgroup path must come from actual qualification; the library never guesses it from the runtime name.


Account-scoped runtime candidate: ops/nixos/rootless-runtime.nix now renders immutable containers/storage/registry configuration and pinned Podman/Quadlet wrappers for the explicitly selected nonroot UID. It selects systemd cgroups, crun/conmon, netavark/pasta helpers, fuse-overlayfs, the bounded /srv/shop GraphRoot/volume/network/tmp paths, a separate volatile /run/user/UID/shop-containers runroot, no pull fallback, bounded file logs and no engine event log. Persistent required subdirectories must already exist with expected ownership; absent storage is not created. The existing read-only startup guard runs with isolated Python before every wrapped Podman command. The wrapper clears inherited environment, including remote endpoints, storage/config overrides and proxy/credential settings; only the systemd notification socket/unit identity are retained for lifecycle operation. The selected /run/user/UID parent must already be a nonsymlink account-owned mode0700 directory. Volatile runroot accounting and all helper paths still need actual cgroup/resource proof.

The generator is explicitly rootless, suppresses kmsg logging, clears inherited environment and restricts QUADLET_UNIT_DIRS to /etc/containers/systemd/users/UID. PODMAN points generated commands to the guarded wrapper. NixOS exposes only account-specific Quadlets and inert /etc/xspi-shop/runtime artifacts. No global generator, PATH installation, Podman socket/service or namespace-helper installation is enabled. Install the generator in the **new account's** per-user discovery path only through a separately reviewed bootstrap/activation step; prevent competing pre-existing generators and inspect actual generated units before any start. That installation and record/image/cluster bootstrap are still unimplemented. No systemctl daemon-reload/activation occurs in evaluation.

The existing /run/wrappers/bin user-namespace helpers are an explicit unqualified prerequisite, not something this module installs or changes. Their actual ownership/modes/range policy, the runtime binary/closure/licences, overlay-on-ZFS compatibility, helper containment, generated command lines, startup and shutdown/missing-mount behavior remain review/off-host tests. Evaluation plus TOML/shell-syntax controls is not execution of the generator or Podman.

References: [Quadlet rootless discovery](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), [containers.conf environment precedence](https://github.com/containers/common/blob/main/docs/containers.conf.5.md), [storage configuration](https://github.com/containers/storage/blob/main/docs/containers-storage.conf.5.md), and the exact upstream [Podman v5.8.8 generator PODMAN override](https://github.com/containers/podman/blob/v5.8.8/pkg/systemd/quadlet/podmancmdline.go). Mutable documentation is guidance; actual compatibility still follows the locked package bytes and qualification.


All four candidate container definitions now set ReadOnlyTmpfs=false and ShmSize=32m, alongside their existing explicit 32MiB /tmp tmpfs. This avoids relying on automatically added writable /run and /var/tmp tmpfs defaults. Actual OCI special-device mounts, effective /dev/shm and tmpfs accounting/permissions, PostgreSQL socket configuration, Caddy/application writable requirements and restart behavior still require off-host inspection. Add any required writable mount explicitly with a bound; do not re-enable implicit mounts to hide a runtime failure. No container was started to qualify this change.


Offline cluster bootstrap is prepared in ops/runtime/bootstrap.py. A separate root-owned /srv/shop/control/bootstrap.json binds the exact action initialize-new-shop-cluster, one-use authorization ID, UTC expiry, qualified machine/account/datasets/paths/resource bounds, an immutable PostgreSQL bin directory and actual initdb SHA256. The bootstrap storage schema has no cluster ID; it cannot satisfy normal startup validation. The normal guard still requires the existing exact PG system identifier/checksums. No authorization record is generated or installed automatically.

The Nix module exposes an inert /etc/xspi-shop/bootstrap artifact only when explicitly enabled. Its isolated Python source bundle admits bootstrap/guard/control source only; the wrapper accepts no arguments (read-only preflight), --help or exactly --apply. --apply additionally requires current record/storage verification immediately before mutation. This is an offline initdb tool under the qualified shop account, not a native PostgreSQL service or an automatic container entrypoint. Actual use remains subject to the host inventory/allowlist/activation and scoped action authorization; repository implementation is not that authorization.

The data and spool directories must already exist, be nonsymlinks, be privately owned mode0700, and differ. PGDATA must be completely empty. A fixed private bootstrap-attempt.json is created exclusively and fsynced with its spool directory before initdb; any prior attempt or result rejects reuse even if PGDATA is empty. The command fixes UTF8/C, checksums, bootstrap role shop_bootstrap and reject-only host/local authentication, retains default fsync and uses --no-clean. Failure/timeout leaves the reservation and any partial data; no automatic cleanup, repair or retry. A separate private, fsynced bootstrap-result.json records only measured system ID/checksums and offline completion; it does not automatically replace normal startup/process evidence or approve a new runtime target.

Only an empty offline cluster is produced. Application database/roles/passwords, runtime postgresql.conf/pg_hba.conf, backup/WAL and protected record publication, per-user generator installation, migrations, app/operator enforcement and container lifecycle are still pending. The reject-only generated HBA is intentional until separately reviewed role/authentication configuration; no default trust or usable password is installed. No currently needed resource credential is missing: this step uses only synthetic local data and no .env secrets.

Local verification: `nix develop ./ops/nixos --command python3 scripts/check.py bootstrap-local`. It runs real initdb as the existing unprivileged development identity in a new token-owned disposable directory, reads the new catalog in single-user mode without a network listener, and checks refusal/uncertainty cases. It does not run the production filesystem/authorization/mount/cgroup path or rootless containers. Initial postgres -C server_encoding was an invalid catalog check; the test now measures all three initialized database catalog encodings directly. See the official [PostgreSQL 18 initdb options](https://www.postgresql.org/docs/18/app-initdb.html) for authentication, checksums, encoding, sync and no-clean behavior.
