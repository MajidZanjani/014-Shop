# Shop secret custody and deployment gates

Operator resource credentials are available in repository .env. Read only the needed value for an authorized operation without printing it. If absent/empty, add a clearly named blank entry/purpose preserving existing values, then ask the user to fill .env directly. No current synthetic build/test needs those credentials.

Runtime application secret key and the new shop database password are separate private files, mounted individually read-only as /run/secrets/shop/secret_key and database_password. No application .env loader, image/store secret, ordinary secret environment, URL or credential dump. Container user 10001 maps to the new qualified shopsvc identity; actual file ownership/mode access must be proven off-host, then qualified for mx1. Production settings enforce bounded regular private files. Secret provisioning/rotation is not performed by the build.

All deployment definitions are candidates and disabled by default. No UID/GID/subordinate range, occupied listener, existing mount/dataset, ingress or public certificate ownership is invented. The Nix module requires explicit qualified IDs, nonoverlap and actual image digests. The readonly startup guard requires root-controlled current machine/account/dataset/PG checksums/system identifier/paths/resource evidence; absent mounts or a new empty PGDATA must fail, never initialize elsewhere. Initial independent cluster bootstrap, password/hba policy and every mutating command require separate exact ownership/destination attestation. ops/runtime/database.py now provides a single-statement INSERT/UPDATE/DELETE execution primitive. It checks actual PostgreSQL system identifier/data directory/database/session and current role/endpoint/durability on the same connection and transaction before DML and before commit, requires fresh runtime evidence both times, and rolls back on denial without automatic retry. The host-side process callback now exists in ops/runtime/process_probe.py and is tied to the SQL primitive through execute_operator_mutation. Real runtime validation, operator command/credential plumbing, and Django/worker integration are still pending. Bootstrap, migrations and other command families remain unimplemented. This is trusted internal SQL, not an interface for user-supplied queries. Metadata reads need narrowly reviewed PostgreSQL privileges; no superuser grant is implied.

No existing PostgreSQL, management socket, privileged/host-network container or shared journal configuration is used. Rootless runtime prerequisites (user namespace helpers, cgroup v2 delegation, storage, generator discovery and selected network stack) need qualification. The module deliberately does not enable global Podman, alter global subordinate-ID helper wrappers or manage all users' lingering. Its new shop-specific linger action is still subject to full activation-impact review before any actual write.

The parent ZFS quota is proposed 80 GiB including descendants/snapshots; the PostgreSQL subtree quota is proposed 50 GiB including data/index/WAL. All GraphRoot/images/volumes/temp/log/certificates/spool and owned backups belong underneath. Actual all-descendant cgroup/helper containment and all writable path accounting are pending off-host tests. A declaration or passing guard does not prove them. Never run disruptive tests on mx1, existing containers or MicroVMs. See docs/qualification-runner.md; no runner assigned.

Pending separately: new component/transitive/bundled licence review, image builds/digests, generated Quadlet compatibility, rootless lifecycle/exhaustion/recovery, immutable database startup/bootstrap wrapper, unchanged public ingress/TLS, actual inventory and complete activation impact. No host activation, DNS/TLS, provider spending or production readiness is authorized by these files.

Local SQL verification: `nix develop ./ops/nixos --command python3 scripts/check.py database-destination`. It creates two token-owned disposable PostgreSQL clusters with synthetic data only. Container/account evidence is a fixture, and the canonical production PGDATA comparison is explicitly adapted in the test to the exact owned scratch path. This lane cannot establish real rootless container or mount identity, and does not satisfy deployment-boot. Implementation follows the official [Psycopg transaction contract](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [prepared-statement constraint](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html) and [PostgreSQL server-identity functions](https://www.postgresql.org/docs/18/functions-info.html).

The host-side process probe loads `/srv/shop/control/database-process.json` only through root-owned, non-group/world-writable, non-symlink ancestors and a bounded regular root-owned file. Its closed record binds the existing startup evidence and SQL destination to an exact PID/start tick/executable/cgroup. Every call rechecks the startup guard, then reads the pinned process directory: PID start time before/after; exact host UID/GID; zero capabilities/no-new-privileges; rootless UID/GID maps with container10001 mapping to the approved host account; exact qualified cgroup including container scope; exact PostgreSQL executable; and the same device/inode/owner for host PGDATA and the process-root PGDATA mount. No Podman command, init, mount, namespace entry, target discovery, record refresh or repair occurs. A restart makes the recorded PID/start time stale until separately authorized evidence refresh; this module cannot approve its own new target.

`execute_operator_mutation` obtains SQL identity from that same record and refuses record changes between checks. It is a **host-side library primitive**, not a deployed operator CLI or an application permission to mount host /proc/control/management resources. Application and worker integration needs a compatible design that retains existing container isolation. Actual runtime permissions (including proc visibility, namespace mapping and pg_controldata/ZFS reads), exact supported scope names and real post-restart behavior remain off-host qualifications. Synthetic parser/loader/wrapper tests do not establish those capabilities. No control record or sample populated PID/UID is installed by this change.

Process-field references: Linux [process start time](https://www.man7.org/linux/man-pages/man5/proc_pid_stat.5.html) and [user namespace mappings](https://man7.org/linux/man-pages/man7/user_namespaces.7.html). The expected cgroup path must come from actual qualification; the library never guesses it from the runtime name.
