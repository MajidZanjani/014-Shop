# Local restore startup fence

This boundary supports disposable local/synthetic PostgreSQL fixtures with fake bank, mail and storage adapters. Actual restoration, traffic/egress isolation, post-point revocation/MFA reconciliation and safe reopening remain unqualified.

For each selected local restore, supply a fresh canonical UUID4 as `SHOP_LOCAL_RESTORE_ID` outside the restored database, before starting any customer, staff or worker process. All cooperating processes must use the same value. Settings import validates the value without connecting to the database. Blank, malformed and production/bank-sandbox selections reject startup with a fixed error. The identifier grants no authority and is never accepted from a customer request.

The selected identity closes private access, customer code capture/verification, both staff factors and new worker/provider effect admissions even when the restored database has an unheld or missing `AccessEpoch`. It creates no recovery history during import, ordinary reads or denied admission. Public catalog and database-connectivity health responses retain their existing contracts; they do not establish recovery readiness.

The existing internal fixture function `shop.access.recovery.local_recovery_operation` requires an exact newly owned test database identity and `shop_test` role, checked against the actual PostgreSQL connection. There is no HTTP or production recovery command.

Call it on an autocommit connection outside any enclosing transaction. Quarantine, release and exact retries reject an atomic or manually managed caller transaction with `recovery_transaction_active` before changing access state. A successful transition commits before the call returns; another connection can observe it immediately. A failed transition still rolls back its complete invalidation/reset. This commit boundary does not establish that actual recovery reconciliation is complete.

Its local sequence is:

1. Record `quarantine` with `request_id` equal to the selected startup identity. This rotates the access epoch and staff generations, consumes pending customer/staff challenges and deletes restored sessions. The matching selected-restore quarantine also disables all restored staff credentials and clears their quotation/business, support, delivery, licence-case, support-refund, overpayment and payment-operation assignments. Immutable business, acceptance, payment, licence, support-work and case history remains intact.
2. Inspect/reconcile synthetic facts while held. Typed bank `lookup` and `lookup_mutation` remain available without new effect admissions. An uncertain result or lookup miss never authorizes resending a financial operation. An unfinished admitted call does not expire; synthetic release refuses until every admitted scope has recorded its exit.
3. Record `release` with `basis_reset` equal to the selected identity and a new request identity. It still requires the current persisted hold and an empty unfinished-admission set, then invalidates access again. This transition represents completed fixture cleanup only.
4. Keep the selected startup identity on subsequent cooperating process restarts. Matching immutable quarantine/release history clears that startup fence, while current database holds continue to close access. Customers must verify afresh. Local staff require the existing explicit `local_staff reset`, both sign-in factors and new assignments for each resource; reset alone supplies no resource authority. A later ordinary quarantine/release preserves assignments and the completed startup sequence. Exact replay of the earlier selected quarantine reports its original removal counts without disabling or deleting newly assigned authority.

Older or unrelated recovery records cannot satisfy a fresh identity. A missing epoch remains closed even with matching old history. Inspection distinguishes `startup_recovery_pending` from the persisted `currently_quarantined` flag; an unheld startup fence does not claim that existing effects have drained.

Private package grant issuance and download consumption lock the valid current customer epoch at the start of their existing transactions, before owner/resource locks. The lock remains held through bounded local archive verification and commit, so quarantine serializes with those transactions. Cached requests from before quarantine/release or a fresh selected restore deny before material work; a fresh verified session is still required afterward. Existing owner, artifact, session, expiry, one-use and archive checks remain. This local package boundary does not establish transport quiescence, actual revocation reconciliation or off-host recovery.

Customer support reservation/release and fixed private follow-up commands also pass the originating request into their existing ledger/follow-up transactions. Each customer command and each private read locks the valid epoch before owner/resource work and retains it through bounded local archive verification and commit. Quarantine or a completed quarantine/release after the view's access check denies even an exact command retry with the fixed `verification_required`403 response; JSON errors contain no ledger or follow-up data, and HTML errors contain no action form. A fresh verified session can resume the same command identity without duplicate history. Staff still require their existing recent MFA and exact resource assignment. Direct trusted synthetic fixture/worker callers can omit the customer request; this is a fence for the explicit customer HTTP boundaries. Transaction serialization does not establish actual transmission, traffic/process isolation, confidential intake or post-point revocation/MFA reconciliation. [Support evidence](../.planning/phases/13-purchase-flow-fulfilment-and-release-acceptance/13-SUPPORT-RECOVERY-PARTIAL.md).

Customer checkout review, acceptance, payment, lookup, grant and staged-delivery actions pass the originating request to their existing owner/resource transactions. Acceptance rechecks at both transactions around archive work; grant and stage publication recheck after archival and before completion. Prepared acceptance/evidence may remain after an interruption, with its completion fields unset. Payment dispatch additionally compares the original customer epoch under its durable admission lock, preventing an already bound prepared attempt from adopting a newly released epoch. Bank/lookup I/O remains outside caller transactions. Quarantine after a one-way claim leaves lookup-only uncertainty; its unfinished admission blocks release until the call exits, and a later lookup miss never authorizes another start. Internal trusted lookup remains available while held. Fresh customer verification resumes exact retained identities without duplicate bank, licence, credit or delivery effects. These local boundaries preserve every actual recovery/provider/revocation/custody/MFA gate. [Checkout evidence](../.planning/phases/13-purchase-flow-fulfilment-and-release-acceptance/13-CHECKOUT-RECOVERY-PARTIAL.md).

Customer cart API and native-form commands also bind their originating request at the existing storage transaction. Private API/editor reads, native command base revisions and private error-page reads acquire the same valid epoch before cart rows. A quarantine or completed quarantine/release after the entry check denies with `verification_required`403 before snapshot creation, version changes or private replay data; denied native responses contain no cart forms. Fresh verification can retry the same retained identity without duplicate snapshots. CAS, catalog checks, immutable history and trusted internal no-request calls retain their existing behavior. These are local database boundaries, not actual transmission or complete recovery qualification. [Cart evidence](../.planning/phases/13-purchase-flow-fulfilment-and-release-acceptance/13-CART-RECOVERY-PARTIAL.md).

Configuration-draft list, get and save also lock the originating epoch before any private draft query. Private response bodies are materialized within those bounded transactions. Recovery after entry authorization or ordinary JSON evaluation denies with the fixed `verification_required`403 response and cannot create a draft or expose a saved retry. Fresh verification resumes the same immutable draft identity without another row. The existing current-catalog admission rule, owner isolation,20-row list bound, CSRF and unaccepted/local-only scope remain. No archive, acceptance or live rights are inferred from saving a draft. [Draft evidence](../.planning/phases/13-purchase-flow-fulfilment-and-release-acceptance/13-DRAFT-RECOVERY-PARTIAL.md).

Quotation JSON and native capture pass the originating request into the existing capture transaction. The valid epoch locks before cart/quotation work, including exact retry and second-key replay of the same snapshot. Private API list/detail and native capture-page/error reads acquire that epoch before resource queries and materialize their response while locked. A quarantine or completed quarantine/release after normal parsing denies with fixed `verification_required`403/no-store and no private form. Fresh verification retains exact request/key identity, captured lines and staff-review history across later cart/catalog changes; trusted fixture calls retain their no-request interface. This is a local database boundary; native history/timeline/document pages and actual transmission/recovery remain separately scoped. [Quotation evidence](../.planning/phases/13-purchase-flow-fulfilment-and-release-acceptance/13-QUOTATION-RECOVERY-PARTIAL.md).

The selected reset, credential disabling, all seven assignment removals, session/challenge invalidation and immutable recovery record commit together. An error rolls them all back. Ordinary temporary holds without the matching selected restore identity retain their existing grant-preserving behavior. Existing operator reset/revoke uses the same finite grant-removal helper and affects only the named staff identity.

Omitting the setting selects ordinary local development behavior. Reusing an identity after another restore can match restored history, so it is unsuitable for a new restore. Stopping old processes, supplying fresh shared configuration and blocking actual traffic/outbound effects belong to the separately authorized recovery procedure. The fixture gate cannot prove those operations, recover lost business facts or reconcile actual MFA recovery codes.
